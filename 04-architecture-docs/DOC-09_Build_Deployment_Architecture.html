DOC-09 — Build & Deployment Architecture Blueprint (Java/React)

The agreed expert-panel architecture for Magnus HMS MVP 1, written so the development team starts Sprint 1 with zero ambiguity: modular monolith on Java 21 / Spring Boot 3, React front-end, one operational branch + remote radiologists (pilot Option A), edge sync as a core MVP 1 service. Every rule below traces to a screen ID in the 225-screen pack (DOC-08 crosswalk) or a design-system pattern (DS-01…DS-11). Version 1.0 · July 2026.

How to read this documentSections 1–5 are code-structure law (module boundaries, events, FHIR naming, data conventions) — violations fail code review. Sections 6–9 are runtime contracts (identity, topology, sync, adapters). Sections 10–11 are ops commitments the pilot SLA depends on. "Screen IDs" refer to the NS design pack (e.g. FO-03 = registration demographics, RD-09 = sign-off, IN-10 = edge sync monitor).

1 · Architecture style — modular monolith (Java 21, Spring Boot 3)

Decision & rationale Panel-agreed · binding
AspectDecisionRationale
StyleSingle deployable Spring Boot 3 application (com.magnus.hms) composed of strictly-bounded modules, verified by ArchUnit rules in CI.One pilot branch, ~15 concurrent staff users: microservices would multiply deployment, sync and debugging cost with zero scaling benefit. No premature microservices.
RuntimeJava 21 (LTS, virtual threads enabled for I/O-bound adapter work), Spring Boot 3.x, Spring Modulith conventions; React 18 + TypeScript SPA front-end.Virtual threads absorb DICOM/HL7/notification I/O without reactive complexity; team skill match.
Extraction pathEach module = own package root, own service interfaces, own events, optionally own DB schema (§2). A module that must scale (first candidates: notification, imaging adapters, sync) can be lifted to a separate service by re-pointing its API interface at an HTTP/AMQP client — no domain-code rewrite.Clean extraction path is the insurance policy that makes the monolith safe to commit to.
Front-endOne React app, route-level code splitting per screen cluster (FO / TK / RD / BL / AD / GV / PL …); patient links (PT-01…PT-12) served as a separate lightweight bundle (no staff chrome, OTP auth only).Patient pages must load fast on low-end phones and must never ship staff code.

2 · Module boundary rules

The five laws Enforced by ArchUnit in CI
#RuleDetail
B1Interfaces or events — nothing elseA module may reference another module only via (a) service interfaces published in that module's …api package, or (b) domain events. Direct access to another module's entities, repositories, or internal packages is a build failure. No shared "common domain" grab-bag; only com.magnus.hms.shared holds pure value types (Money, Mrn, AccessionNo, AuditRef) with zero JPA annotations.
B2Transactional outboxDomain events are published inside the producing transaction via Spring ApplicationEventPublisher and written to the module's outbox_event table in the same commit. A relay (Spring Modulith event externalisation) forwards committed events to RabbitMQ for external consumers (notification workers, sync, analytics feed). Internal consumers use @ApplicationModuleListener (async, after-commit). Never dual-write: no direct AMQP publish from request threads.
B3One PostgreSQL, schema-per-domain optionalSingle PostgreSQL 16 instance per plane (cloud + branch edge). Modules default to one schema; a module may opt into its own schema (billing.*, audit.* do so from Sprint 1 — money and audit isolation). No cross-module joins, ever — even inside one schema; cross-context reads go through the owning module's query service. Flyway migrations are namespaced per module.
B4Redis where justified onlyRedis is approved for: OTP + secure-link token store (PT-01/PT-03 TTL), queue-display fan-out (FO-14/SC-10), rate limiting, idempotency-key cache on ingestion (§8). It is not a system of record; anything needed after restart lives in PostgreSQL.
B5Synchronous chains stay shortA request handler may call at most its own module + read-only queries on others. Anything with side effects in a second module goes through an event (e.g. BL charge on OrderPlaced, NT dispatch on ReportReleased) — this is also what makes the edge/cloud split (§7–8) tractable.

PrincipleWe do not run a FHIR server in MVP 1 — but every core entity is named and structured after its FHIR R4 resource, so future LIS integration, ABDM/ABHA linkage and HIE participation are adapter work (mapping at the edge), never a data-model remodel.

5 · Data conventions

Non-negotiable data rules Apply from first migration
ConventionRule
Optimistic locking + freshnessEvery clinical entity carries @Version version BIGINT and last_modified TIMESTAMPTZ + last_modified_by. Stale-write → 409 with DS-05 conflict UI. These columns also drive sync change-detection (§8).
API versioningAll REST under /api/v1/… from day one. Breaking change = new /api/v2 resource, never mutation of v1. Patient-link endpoints live under /link/v1/… (separate gateway policy, OTP auth).
Audit event catalogueImmutable append-only audit.audit_event (INSERT-only role; no UPDATE/DELETE grants). Typed catalogue, extended only via PR to AuditEventType enum: PATIENT_CREATE, PATIENT_VIEW, PATIENT_MERGE, ORDER_PLACE, ORDER_CANCEL, STUDY_ACQUIRE, REPORT_SIGN, REPORT_AMEND, REPORT_RELEASE, CRITICAL_RESULT_FLAG, CRITICAL_RESULT_ACK, CRITICAL_ESCALATE, PAYMENT_CAPTURE, REFUND_PROCESS, CONSENT_CAPTURE, CONSENT_WITHDRAW, BREAK_GLASS_OPEN, STEP_UP_CONFIRM, ACCESS_DENIED_MASKED, FORM_F_FILE, MIGRATION_BATCH_ACCEPT, SYNC_CONFLICT_RESOLVE, EXPORT_GRANT, JOB_ESCALATION. Viewers: AD-20 (branch), GV-02 (governance), PL-07 (platform mirror).
Number series (AD-16)Single formats, one registry, gap-tracked: MRN MG-{branch}-{YYYY}-{seq6} · accession AC{branch}{YYMMDD}{seq4} · invoice INV/{branch}/{FY}/{seq6} (GST-compliant, C-5c) · receipt RC/{branch}/{FY}/{seq6} · credit note CN/{branch}/{FY}/{seq4}. Edge nodes draw pre-allocated ranges from the registry so offline issuance never collides (§8).
Moneyamount_minor BIGINT (paise) + currency CHAR(3) = 'INR' everywhere. No floats, no BigDecimal columns. Rounding rules live in one shared.Money type; GST computed line-wise then totalled (C-5).
TimeStorage/UTC (TIMESTAMPTZ), display/IST (Asia/Kolkata) applied in the React layer only. Business dates (cash session day BL-09, Form F cutoff IR-02, regulatory calendar) are explicit DATE columns computed in branch timezone, never derived ad hoc from timestamps.
IdentifiersPrimary keys = UUIDv7 (time-ordered). Human identifiers (MRN/accession/invoice) are unique business keys, never PKs, never recycled — merges retire, they don't delete (FO-09).

6 · Identity & access — Keycloak + OTP links

Realms, tokens, step-up AU cluster · DS-06
ConcernDesign
Keycloak realmsThree realms: magnus-staff (all branch/HQ roles; 2FA per AU-03/04, lockout AU-02, recovery AU-05/AU-14), magnus-referrer (referring doctors DD-01…DD-11; attribute-restricted — token carries referrer_id, and every query is forcibly scoped to that referrer's own patients, DD-07), magnus-operator (platform PL-01…PL-12; hardware-key 2FA, dual-control break-glass PL-12). Realm settings surfaced in AU-15/AU-16.
Patient sideNo patient accounts in MVP 1. Patients receive secure links (PT-01) and authenticate with OTP per link session; tokens are short-lived, link-scoped, stored in Redis with TTL (PT-03 renewal, D-12 standardised TTL). Rate limits + resend rules per DS-08.
React authSPA uses oidc-client-ts with Authorization Code + PKCE; no implicit flow, no tokens in localStorage (in-memory + silent renew). Workspace/branch context switch (AU-10) re-mints the token with the selected branch claim.
Roles → authoritiesKeycloak realm/client roles map 1:1 to Spring Security authorities (ROLE_RECEPTION, ROLE_TECHNICIAN, ROLE_RADIOLOGIST, ROLE_BRANCH_ADMIN, ROLE_PO_DPO, … per AD-04). Method security (@PreAuthorize) at every module API interface — module boundary is also the authz boundary. Masked-denial responses (C-7/NS-14, DD-06) implemented in identity, not per screen.
Step-up (AU-09)Sensitive actions (report sign RD-09, refund BL-06, merge FO-09, break-glass DD-05, migration accept AD-12) require a fresh confirmation: backend issues a short-lived step-up token (≤5 min) bound to the session AND the target object ID; the mutating endpoint accepts the action only with a valid matching token. One token, one action, one object — replay across objects is impossible. Every issuance + use → STEP_UP_CONFIRM audit.

8 · Edge sync module — core MVP 1 service, not deferred

Sync mechanics com.magnus.hms.sync · DS-04 · IN-10
MechanismDesign
Edge outboxEvery edge-side committed transaction that must reach cloud writes an outbox_entry (same transaction, per B2): entity snapshot ref, event type, correlation_id (UUIDv7), sequence per aggregate.
Batched pushRelay ships ordered batches (≤500 entries or 30 s, whichever first) over mTLS HTTPS to /api/v1/sync/batches. Backpressure-aware; resumes from last acked sequence after outage.
Idempotent ingestionCloud ingestion dedupes on correlation_id (Redis idempotency cache + unique constraint). Replaying a whole batch is always safe; partial-batch failure returns per-entry status.
Conflict routingVersion check on apply (§5 version column). Non-clinical, non-overlapping fields → last-writer-wins with audit note. Clinical fields → never auto-merged: conflict lands in the four-eyes queue (IN-10), resolved by an authorised reviewer, resolution audited as SYNC_CONFLICT_RESOLVE.
Master data downstreamCloud→edge: masters (catalog, price lists, templates, schedules, terminology) versioned snapshots pulled on change + on reconnect; edge reads masters only from local cache, never live from cloud in request path.

11 · SLA engine

Deadlines, sweeps, escalations DS-03 pattern · AD-18 jobs
ElementDesign
ColumnsEvery SLA-bearing row (Study read, critical-result ack, delivery recovery task, grievance, privacy-rights request, Form F filing) carries sla_deadline TIMESTAMPTZ + sla_status (ON_TRACK | AT_RISK | BREACHED | ESCALATED | STOPPED), set at creation from the DS-03 configuration (per priority tier, per branch hours where configured).
Sweep jobScheduled sweep (registered + monitored in AD-18) runs every 60 s: flips AT_RISK at the configured warning fraction, BREACHED at deadline, and fires the configured escalation action per DS-03 — notify owner → notify supervisor → escalate tier (e.g. critical-result ladder RD-11/NS-01). Sweep is idempotent and safe to re-run; missed runs surface as AD-18 job alerts.
Clock stopsTerminal events stop clocks via the event stream, not polling: ReportSigned stops the read clock, CriticalAcknowledged stops the ack clock and cancels pending escalations, resolution states stop grievance/recovery clocks.
AuditEvery auto-escalation writes JOB_ESCALATION (and critical-path ones additionally CRITICAL_ESCALATE) to the append-only audit stream with the rule version applied — SLA behaviour is fully reconstructible for governance review (GV-02) and pilot reporting (AD-13).

Everything above is the agreed contract; deviations go through the panel as an ADR.

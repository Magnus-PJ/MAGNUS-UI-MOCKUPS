DOC-10 — Test Traceability & Safety-Gate Test Suite

Proves that no workflow dead-end is missed across the 225-screen complete pack: every end-to-end scenario from DOC-01 is decomposed into an ordered screen chain, tied back to the signed scope-checklist features, and covered by numbered test cases. UAT scripts derive directly from this matrix — a scenario row here becomes a UAT script; a safety-gate row becomes a mandatory pass/fail gate before sign-off. Version 1.0 · July 2026.

1 · Method — how traceability worksRead first
ElementRule
ScenarioOne of the 25 end-to-end patient/operational journeys from DOC-01 Patient Scenarios (same numbering S01–S25). A scenario is the unit of UAT: it starts at a real-world trigger and must end in a terminal state on a real screen — never in a dead-end.
Ordered screen chainThe exact screens crossed, in order, using pack screen IDs (e.g. FO-02 → FO-03 → …). Every chain implicitly begins at AU-01 sign-in (or PT-01 OTP for patient-side steps); these entry screens are not repeated in each row. Branch points are shown with the screen that resolves them.
Checklist refsFeature items from the signed scope checklist (#50–#78 workflow features, plus #12–#16 platform/offline and #103 integration items) that the scenario exercises. Every checklist item claimed as “in scope” must appear in at least one scenario row.
Test case IDsNumbered TC-NNk where NN = scenario number, k = case sequence (e.g. TC-021 is the first test of Scenario 02). Each carries a one-line assertion; the full UAT script (data, steps, expected screenshots) is generated from this ID.
Severitysafety-critical patient-safety consequence if it fails · statutory legal/regulatory consequence (PC-PNDT, DPDP, GST, AERB) · operational revenue/ops consequence.
Acceptance ownerLeft blank for the client to fill during UAT planning — name of the person who signs off that scenario. A scenario without a named owner cannot enter UAT.
Pass ruleA scenario passes only when every TC in its row passes and every safety gate (Section 3) whose screens appear in its chain passes. Safety gates are absolute: one failed SG blocks UAT sign-off for the whole release, regardless of scenario-level results.

3 · Mandatory safety-gate test suite — must pass before UAT sign-off
Hard ruleThese 12 gates are pass/fail for the release, not for a scenario. A single failing SG blocks UAT sign-off even if all 25 scenario rows pass. Each gate is re-run on every release candidate; results are attached to the sign-off certificate.
IDGiven / When / ThenScreensExpected block behaviour
SG-01
Given a contrast CT order for a patient with no creatinine/eGFR result within 30 days and no physician risk-acceptance on file
When any user attempts to move the study to Perform
Then the order is blocked at screening with the missing-lab reason displayed
CS-01·OR-02Perform action disabled with inline reason; only two exits offered — record a lab result, or route to physician risk-acceptance (CS-04). No silent bypass, no free-text waiver.
SG-02
Given an MRI order whose MR-safety screening has any metallic-implant answer of YES
When the study is scheduled or sent for acquisition
Then a hard-stop holds the study until a radiologist countersigns the safety decision
CS-02Status locked at “MR safety hold”; TK-01 shows Blocked; countersign control is visible only to the radiologist role; all other roles see a read-only hold banner.
SG-03
Given a radiology order for a female patient of childbearing age
When the order is submitted without LMP / pregnancy status captured
Then submission is refused until the field is completed (including “unable to determine” with reason)
OR-01·CS-01Order form validation blocks submit; the pregnancy-status field is mandatory-highlighted; the captured value travels with the order and is shown at TK-01 and RD-07.
SG-04
Given an obstetric ultrasound order
When the technologist attempts to start acquisition with Form F incomplete or missing the patient signature
Then the study cannot reach Perform
CS-06·TK-01TK-01 row shows “Form F pending”; Perform disabled; the only forward action deep-links to CS-06. Signature pad state (unsigned) is itself a blocker, not just form fields.
SG-05
Given a screening outcome of Blocked on any safety checklist
When the technologist attempts to override it themselves
Then no self-override path exists — override is physician-only via CS-04 with step-up auth
CS-04·TK-01Technologist role sees no override control anywhere in the flow; CS-04 requires physician credentials + step-up re-auth + typed clinical justification; the override is attributed and audit-logged.
SG-06
Given an acquisition where fewer series were received than the protocol expects
When the study is pushed toward the reading worklist
Then release to reading is blocked until a partial-study override is recorded
TK-02·RD-01TK-02 shows the series-count mismatch; “Send to reading” disabled until an override with reason is recorded; RD-01 displays a partial-study badge so the reader knows what is missing.
SG-07
Given a result flagged critical
When any user attempts to close the critical-result item
Then closure requires referrer acknowledgement or a fully exhausted escalation ladder — nothing else
RD-11·DD-02Close action disabled while unacknowledged and ladder tiers remain; each tier attempt (call/SMS/covering physician) is logged; “exhausted” state requires the final-tier outcome recorded before close is enabled.
SG-08
Given a signed report
When any user (including the author) attempts to edit it
Then the signed version is immutable — correction is possible only through a versioned addendum
RD-09·RD-12No edit control on a signed report anywhere in the product; RD-12 creates v2 linked to v1; v1 remains retrievable byte-identical; distribution always carries the latest version plus history.
SG-09
Given an equipment AERB (or PNDT) registration that has expired
When anyone attempts to schedule, acquire on, or sign a report from that machine
Then all three actions are blocked until a valid registration is recorded
AD-09Expiry flips the machine to Blocked in SC-05/FO-10 (no slots), TK-01 (no acquire), and RD-09 (no sign for studies acquired after expiry); each refusal names the registration and expiry date.
SG-10
Given an unpaid or partially-paid invoice with a report flagged critical
When the release queue evaluates the payment-hold policy
Then the critical report bypasses the payment hold and is released/delivered immediately
BL-20BL-20 policy engine shows the bypass rule as non-configurable-off for critical results; the release is logged with “critical bypass” reason; billing follow-up continues separately without delaying care.
SG-11
Given a branch that worked offline and queued registrations, invoices and payments
When connectivity returns and the queue replays — including a forced double replay
Then replay is idempotent: zero duplicate MRNs, invoice numbers or receipts
DS-04·IN-10IN-10 shows each queued item exactly once with a terminal state; re-running replay produces “already applied” results, not new records; series numbering (AD-16) has no gaps or repeats.
SG-12
Given a user without access to a patient record
When they hit an access-denied state via search, deep link, or access request
Then the denial screen leaks zero demographics — no name, age, sex, contact, or study detail
DD-06·DS-07Denial views render only the masked identifier pattern from DS-07; page title, breadcrumb, URL preview and notification text are all checked for leakage; the denied attempt itself is audit-logged.

5 · How to extend this matrixKeep the no-dead-end guarantee alive
StepActionRule that keeps the guarantee
1New screen → add to a chain. When a screen is added to the pack (new ID in a cluster), insert it into the ordered chain of at least one existing scenario, or write a new scenario row if it opens a genuinely new journey.A screen that fits no chain and is not a setup/admin dependency is a design smell — it is either a dead-end or unnecessary. Do not merge it.
2Add test cases. Give the screen 1+ new TCs under the scenario's numbering (next free TC-NNk), each a single-line assertion covering the screen's forward action and its failure exit.Every TC must assert both “it works” and “when it can't, the user still has a way out.”
3Check the gate list. If the screen touches ordering, screening, acquisition, signing, critical results, statutory filing, offline replay, or access denial, decide whether an existing SG covers it or a new SG-13+ is needed — with the compliance owner's sign-off.Safety gates only ever grow. Removing or weakening an SG requires a documented risk acceptance from the client's clinical lead.
4Update the coverage table. Re-run the generator so Section 4 counts refresh, and fill the acceptance-owner cell for any new scenario before it enters UAT.The build fails on an unreferenced screen ID — so the matrix can never silently fall behind the pack.

Audit is a first-class subsystem, not a side effect: every one of the 225 screens carries an audit line (DS-11 pattern) stating what viewing/acting on that screen records.

1 · Design principles

#PrincipleImplementation consequence
P-1Append-only, write-onceAudit store accepts INSERT only. No UPDATE/DELETE grants for any application role, including DBA service accounts (AU-18 keys are scoped write-only to the ingest endpoint). Corrections are new events referencing the corrected event.
P-2Audit before commitThe audit event is written in the same transaction (transactional outbox) as the business mutation. If the audit insert fails, the business action fails. Reads are audited asynchronously with at-least-once delivery and a 60-second flush SLA.
P-3Pseudonymised subjectAudit rows never carry patient name/phone/address — only the surrogate patient_ref (opaque UUIDv7) plus masked MRN display form #MRN-••••30 for UI rendering (same masking as denial screens, DD-05/DD-06).
P-4Purpose-of-use on every eventEvery API call carries a X-Purpose-Of-Use header set by the client from screen context (TREATMENT, PAYMENT, OPERATIONS, EMERGENCY, LEGAL, PATIENT-REQUEST, RESEARCH-DEIDENT). Missing header → 400 in non-prod, logged anomaly in prod.
P-5Tamper-evident, not tamper-proofSHA-256 hash chain per branch-day partition, daily anchor persisted to the platform ledger (PL-07). We detect modification; prevention is layered (P-1 grants + storage immutability policy).
P-6Audit of auditOpening AD-20 / GV-02 / GV-03 / PL-07, running an audit search, or exporting audit data is itself an audit event of category SECURITY (§4.6).
P-7Data residencyAudit store, log store and metric store reside in Indian regions only (GV-14). Cross-border export of audit extracts requires GV-15 export-governance approval.

Any screenUser action / record open (DS-11 audit line)

→
audit-svcValidate schema, compute chain_hash, append
→
PL-07Daily anchor + integrity verification job
→
AD-20Org audit viewer (search, filter, export)
→
GV-02/03Review workflows (sampling, break-glass)
Ingest transport
Kafka topic audit.events.v1, partition key = branch_id; ordering guaranteed per branch (required for hash chaining).
Offline branches
FO offline-first mode (IN-10 edge sync) queues audit events locally with an offline_seq; on reconnect they are appended with original device timestamps preserved and a sync_lag_ms annotation. Chain hash is computed at server append time, never on the edge.
Clock discipline
All servers NTP-synced; events store ts_utc authoritative + derived ts_ist (UTC+05:30) for display and regulator exports (IR-02, IR-05 expect IST).
Idempotency
event_id is a client/service-generated UUIDv7; duplicate ids are dropped on ingest (at-least-once transport, exactly-once store).

7 · Tamper-evidence & review workflows

7.1 · Hash chain & integrity verification
appendchain_hash = SHA-256(prev ‖ event) per branch-day
→
00:30 ISTNightly job re-verifies yesterday's chain end-to-end
→
PL-07Terminal hash anchored to platform ledger (separate trust domain, operator-controlled)
→
AD-20Org viewer shows per-day integrity badge: VERIFIED / PENDING / FAILED
→
GV-08/09FAILED ⇒ P1 incident + breach runbook, CERT-In 6 h clock
Trust separation
Anchors live in the platform-operator domain (PL-07); org admins (AD-20) can read but not write anchors. An attacker must compromise both domains inside one anchoring window (≤ 24 h) to hide a modification.
On-demand check
AD-20 "Verify range" re-computes any date range; result itself logged as SEC-0601 + SEC-0606.
Spot re-anchor
Weekly, a random 1% of historical branch-days are re-verified against their anchors (defence against slow storage rot).

8 · Operational (application) logging

The NO-PII rule Application logs (stdout/JSON to the log store) may never contain: patient name, phone, address, full MRN, Aadhaar/ID numbers, report text, or free-text fields. Allowed identifiers: patient_ref UUID, order/invoice ids, masked MRN #MRN-••••30. This is what lets us keep app logs 180 days on cheaper, wider-access infrastructure than the audit store.
ControlSpecification
Structured loggingJSON lines; mandatory fields: ts, level, service, trace_id, span_id, branch_id, msg. trace_id = W3C traceparent, propagated GW → services → Kafka headers; joins app logs to audit events for incident forensics.
PII scrubberLogback/Log4j2 filter with deny-list regexes (10-digit phone, Aadhaar pattern, MRN pattern, email) runs on every appender in every service — defence in depth behind developer discipline. Scrub replaces with [REDACTED:type] and increments metric logs_pii_scrubbed_total.
Violation routelogs_pii_scrubbed_total > 0 alerts the owning team same-day (a scrub means code tried to log PII). Confirmed PII that reached the log store = data incident: open GV-08, run purge playbook (targeted deletion from log store — permissible because logs are not the audit record), assess under GV-09 breach runbook incl. CERT-In 6 h evaluation, add regression test.
Log levels in prodINFO default; DEBUG only via AD-17 feature toggle, per-service, auto-expiring in 4 h, toggle flip logged ADMN-0504.
Access controlLog store read access = engineering on-call group only, via SSO (AU-16 realm), session-recorded; access reviewed in GV-02 quarterly privileged review.

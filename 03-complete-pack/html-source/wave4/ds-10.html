DESIGN SYSTEM
G17 Design System & Patterns — documentation pages
Baseline: NET-NEW · i18n & localisation pattern
Purpose & workflow: Rules for what Magnus translates, how Indic scripts render, and how locale interacts with legal notice versions. MVP-1 ships English (en-IN), Hindi (hi-IN) and Marathi (mr-IN). Staff UI locale is a per-user preference; patient-facing locale is a per-patient communication preference captured at registration.
STATE A — WHAT-IS-TRANSLATED MATRIX
Translation scope by surface locales: en + ml (Malayalam — pilot), hi/mr/ta ready
SurfaceTranslated?MethodRationale & rules
UI chrome (nav, buttons, labels, errors)YESManaged string catalogue100% key coverage gate in CI; a missing hi/mr key blocks release, falls back per chain (State C) at runtime only for hotfixes.
Patient comms (SMS, WhatsApp, portal)YESPer-locale approved templatesEach DLT SMS template is separately registered per language on the Jio route — translation is a new template ID, not a string swap. WhatsApp BSP templates likewise pre-approved per locale.
Consent forms & privacy noticesYESLegal-reviewed translations, versionedTranslations are legal texts, not string files. Each locale rendition carries its own reviewer sign-off and is bound to the notice version (State C). Patient signs the rendition they were shown.
Clinical reports (radiologist narrative)NOAuthored language only (English in MVP-1)Never auto-translated. Machine translation of clinical findings is a patient-safety risk (negation, laterality, hedging nuance) and creates an unowned legal document — no clinician has signed the translated text. Portal shows a hi/mr help note explaining how to get findings explained, but the report body stays as signed.
Master data (test names, modality names)PARTIALPatient-facing aliases onlyInternal catalogue stays English/coded (CT BRAIN PLAIN). Patient-facing alias per locale (“सीटी स्कैन — मस्तिष्क”) used on slips and portal only; invoices always print the English catalogue name + code beside any alias.
Audit logs, IDs, device namesNO—Log events, AE titles (MERIDCT1), document numbers are locale-invariant; only rendered timestamps localise.
Implementation notereact-i18next integrated from Sprint 1 even while only English strings ship — retrofitting i18n into components is the expensive path.

STATE B — SCRIPT RENDERING & NUMBER/DATE LOCALE RULES
Script rendering rules Devanagari (hi, mr)
RuleSpec
Line heightDevanagari needs headroom for matras and conjunct stacks: body line-height 1.7 (vs 1.45 Latin); buttons/chips min-height +2 px in hi/mr locales — components must not clip शिरोरेखा or descenders.
Font stack"Noto Sans Devanagari", "Mukta", sans-serif; embedded subset in PDF/A output (per DS-09). Never rely on OS fallback for print.
Type scaleDevanagari at same pt renders visually smaller — bump 1 px at sizes ≤ 13 px in hi/mr locale packs; never mix scripts mid-word.
TruncationNever ellipsis-truncate inside a conjunct cluster; truncate on word boundaries only. hi/mr strings run ~15–20% longer — layouts must pass the pseudo-locale expansion test in CI.
DigitsAlways international digits 0–9 (not ०–९) in all locales — clinical/billing safety rule; applies to slips, portal and SMS.
BidiNot applicable in MVP-1 (no RTL locale); layout stays LTR for hi/mr.

STATE C — FALLBACK CHAIN & NOTICE-VERSION BINDING
Fallback chain runtime resolution order
1 · Exact locale
mr-IN string / template / notice rendition
2 · Language default
mr → hi is not assumed; each language falls back independently to…
3 · en-IN (platform base)
Always complete by CI gate; guaranteed terminal fallback for UI chrome and master-data aliases.
✕ No fallback for legal texts & DLT templates
A consent notice or registered SMS template with no rendition in the patient's preferred locale is not silently swapped to English — the flow surfaces an explicit choice: “Marathi version unavailable for notice v4 — proceed in English?” with staff attestation, logged.

Fallback events emit telemetry (i18n.fallback with key + locale) so the localisation backlog is data-driven; > 50 hits/week on one key raises an amber task for the org admin.

Binding ruleA translation is valid only for the exact notice version it was reviewed against. Publishing notice v5 automatically demotes all v4 renditions to PENDING REVIEW — the consent flow then applies the no-fallback rule above until each locale is re-approved (legal reviewer + org admin, four-eyes).

Consent records store: notice version + locale rendition ID + rendition hash actually displayed — what the patient saw is provable byte-for-byte.

Locale preference changes, fallback attestations and notice-rendition approvals are recorded in the access log.

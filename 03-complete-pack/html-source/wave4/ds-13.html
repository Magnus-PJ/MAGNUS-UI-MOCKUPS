DS-13 Concurrency, Presence & Same-Patient Collaboration Pattern

DESIGN SYSTEM
G17 Design System & Patterns — documentation pages
Baseline: NET-NEW · client input 26-Jul (multiple operators on the same patient at the same time)
Purpose & workflow: In every Magnus branch the same patient is touched by several operators at once — front office corrects a phone number while the cashier collects payment while the technologist opens the visit at the modality and a radiologist pulls priors. This page is the product-wide contract for that reality: presence awareness, section-scoped edits with optimistic locking, a normative concurrency matrix (what may run in parallel, what serialises, what blocks), and the live-refresh rules that keep every open screen truthful without anyone pressing reload. Nothing in Magnus ever silently overwrites another operator's work.
STATE A — PRESENCE: WHO ELSE IS ON THIS RECORD, LIVE
Presence strip — appears on every patient/visit-scoped screen component: .presence
● You · Front Office ● P. D'Souza · Billing — collecting invoice INV/NPV/26-27/0430 ● T. Okafor · CT console — visit open (acquiring) ● Dr. S. Menon · Reading — viewing priors (Irinjalakuda)
RuleSpecification
Where shownAny screen scoped to a patient or visit (FO-06 patient 360, BL billing, TK worklists, RD reading, DD referrer view). Renders under the pinned patient-context bar (DS-12). Empty when you are alone — the strip collapses to nothing, never a "0 others" message.
What it statesOperator display name · role · what they are doing (the screen's declared activity verb) · branch if different from yours. Identity is a name + role, never a photo; patient-facing displays (queue boards) NEVER show presence.
FreshnessHeartbeat every 10 s; an entry older than 30 s greys out; older than 2 min it is removed. Presence is advisory — it never locks anything by itself.
AuditPresence is telemetry, not an access event. Opening the record is the audited event (per DOC-05); the strip just makes it visible to peers in real time.

STATE B — SECTION-SCOPED EDITS + CONFLICT DIALOG (ONLINE TWIN OF DS-04)
Optimistic locking, per section — not per record normative
Contract clauseSpecification
Edit unit = sectionA patient record is edited in independent sections (demographics · contact · insurance/TPA · consent · billing lines · clinical). Each carries its own version. Two operators editing different sections of the same patient never conflict.
Same-section collisionSave sends the section version it was loaded with. Stale version → HTTP 409 → the conflict dialog below. No last-write-wins, ever, for clinical or financial fields.
Soft edit signalThe moment an operator focuses a field in a section someone else has open, both see an amber hint on that section header: ✎ Also being edited by D. Nair. Advisory only — typing is never blocked.
No-op mergesIdentical values arriving twice auto-merge silently and are logged (concurrent_edit_noop), same as DS-04 queue rule.

STATE C — THE CONCURRENCY MATRIX (NORMATIVE — WHAT RUNS IN PARALLEL)
Same patient, same time — allowed combinations
Operation A ∥ Operation B (same patient)VerdictMechanism
Demographics edit ∥ Billing collectionPARALLELDifferent sections; invoice snapshots demographics at creation.
Registration desk ∥ Technologist opens visit at modalityPARALLELVisit state machine; acquisition needs ARRIVED, later demographic edits do not touch the study.
Cashier collects ∥ Radiologist reads priorsPARALLELRead never locks; release-policy check (BL-20 / D-21) evaluates at sign-out, not during payment.
Two cashiers ∥ same open invoiceSERIALISEDPayment capture takes a 90 s exclusive intent on the invoice; second cashier sees "P. D'Souza is collecting — ₹2,850 UPI in progress" with live status, not an error.
Consent capture ∥ Order creation needing that consentSERIALISEDOrder screen shows consent status live; the Create button enables the moment consent lands — no refresh.
Report editing ∥ Report signingBLOCKEDSign takes an exclusive lock on the report version (D-26 hash binding); editor sees "signing in progress" and their draft becomes an addendum path if sign completes first.
Same operator, two counters/devicesSERIALISEDSecond device sign-in shows AU-19 device-trust prompt; write actions bind to one active device at a time per role session.
Merge (FO-04 duplicate-merge) ∥ anything elseBLOCKEDMerge is the only whole-record lock in the product: 60-second exclusive window, everyone else sees a countdown banner; queued actions replay against the surviving MRN.

Anything not listed defaults to PARALLEL with section locking. New modules must add their rows to this matrix before build — the matrix is a contract, not documentation.

STATE D — LIVE REFRESH: SCREENS STAY TRUE WITHOUT RELOAD
Live-update contract for lists, queues and detail panes
RuleSpecification
In-place row updatesWorklists, queues, billing lists and the token board update rows in place (2 s server push cadence). A changed row pulses once (.simrow-style highlight, 1.2 s) — no full-table reflow, no scroll jump, no unread-badge games.
Sort stabilityA row whose sort position changes moves only on the next natural repaint (filter change, pagination, manual refresh) — rows never jump out from under a hovering cursor. New rows enter at their sorted position dimmed for 1.2 s.
Detail-pane stalenessAn open detail pane whose record changed elsewhere shows a slim header chip Updated by P. D'Souza 11:42 — refresh. Clinical-safety fields (allergy, pregnancy, eGFR) hard-refresh immediately with a one-line notice; everything else waits for the user.
Action guardsEvery state-changing button re-validates server-side against current state, not screen state (DOC-13 contract). The stale-click answer is a precise message ("This invoice was settled by P. D'Souza at 11:42"), never a generic failure.
Walk-in ∥ booked convergenceBoth intake paths (Flow 2 booked · Flow 3 walk-in) feed one visit queue; the token board and technologist worklist show the merged stream live, so simultaneous registrations at two counters never double-issue a slot or token.

Audit: every live push carries the origin action id — support can answer "why did this row change on my screen" from GV-01 in one lookup. Cross-refs: DS-04 (offline twin) · DS-12 (context bar) · FO-04 (merge lock) · BL-04 (payment intent) · RD-09 (sign lock) · DOC-02 Flow 17.
